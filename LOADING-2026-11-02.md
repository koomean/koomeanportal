# Portal data loading state

Initial empty arrays were rendered by `applyLanguage()` before the bootstrap request returned, so the first real UI could incorrectly say there were no applications. The render path now uses explicit `dataStatus` values: loading, ready, error.

The catalog and social rail show localized status labels with a CSS spinner while bootstrap is pending. Unknown counts use a dash. Existing cards and social links remain available during refresh, with an inline loading indicator. Search, favorites, routing and language changes preserve the pending state. A successful empty response shows the real empty message; a failed empty response shows the existing retry/error UI. A superseded request cannot settle a newer loading state. Reduced-motion visitors retain a visible icon and label without rotation.

Verification ledger:

- Before the fix, three focused Node regressions failed: pending count reported0, no settled loader lifecycle existed, and error re-rendering could become an empty state.
- After the fix,29 Node checks passed. CUA preview delayed bootstrap5seconds and observed `aria-busy=true`, a visible spinner with `animation-name:spin`, no false empty message, then normal catalog data after the response.
- Browser regressions hold requests explicitly for pending search/routing/language/favorites, actual empty success, failed first load, retained refresh and an old authenticated response racing a newer anonymous load.
- Local preview supports `PORTAL_PREVIEW_BOOTSTRAP_DELAY_MS=5000 npm run preview`; the delay is a development-only helper and never enters production assets.

- Branch run41463256154 passed all11 new loading regressions, then an existing dialog test sampled focus before the dialog's requestAnimationFrame focus handoff. That test now waits for the actual focus handoff before asserting the same workspace/sidebar isolation behavior. The dialog implementation is unchanged.
